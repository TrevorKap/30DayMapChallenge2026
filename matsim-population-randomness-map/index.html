Seeded City

A synthetic population isn't measured — it's rolled. This model runs, in the browser and over Budapest's real road network, the randomization steps from a real open-source MATSim population generator originally built for Alexandria, Egypt1: take an aggregate travel count between two map tiles, then manufacture individual commuters to match it. Each commuter gets a random point inside their home tile, a random point inside their destination tile, a random departure time in the 7–10am window, and a random travel mode drawn from real citywide splits: 43.4% car, 56.6% transit — then drives or rides the actual Budapest streets between them, routed live through the Mapbox Directions API. No two of these commuters are real people — but press Reseed and watch a brand-new random population converge back to the same fixed splits anyway.

1 This piece reimplements, client-side, the randomization steps from MATSim Syn_pop_genrator.ipynb (go-hary/Facebook-to-MATSim), an open-source notebook that builds a MATSim agent-based travel model for Alexandria, Egypt from Meta's Data for Good Movement Range Maps, written for Elgohary, Casier, Pucci & Witlox, “Using Social Media Data to Construct an Agent-Based Model in a Data-Scarce Environment: A Case Study of Alexandria, Egypt,” Journal of Urban Technology (2025). Three steps are reproduced faithfully: a uniformly random point is dropped inside each origin and destination tile, exactly as the notebook's generate_random_points() does by rejection-sampling inside a polygon; each trip draws a uniformly random departure time between 07:00 and 09:59, exactly as the notebook's random.randint call; and each trip draws its transport mode (car 43.37%, public transit 56.63%) and destination activity (work 50.3%, education 43.3%, business 4.3%, leisure 1.3%, shopping 0.8%) from the same fixed probabilities passed to the notebook's np.random.choice calls — activity type is drawn independently of which tile a trip lands in, matching the notebook's method, so a tile's name here isn't a guarantee of what happens there. What's different from the notebook: the geography is Budapest, Hungary, not Alexandria — the notebook's real input (Meta's tile-to-tile Movement Range OD matrix and its matching quadkey shapefile) is for Alexandria and isn't published in the repository anyway, so this transplants the same randomization method onto a different, real city instead of guessing at Alexandria's actual numbers. The nine home tiles and three activity tiles are real Budapest neighborhoods (their relative weights are an illustrative stand-in for residential/job density, not measured). Each trip's path is real, though: once every home-tile-to-hub-tile pair is drawn, its road route is fetched live from the Mapbox Directions API (driving profile, real OSM-derived street geometry) and every commuter on that pair rides the same real streets between their own random origin and destination points; a pair falls back to a straight line only if that one Directions request fails. Every tile is a real Bing/Google-style slippy map tile at zoom 14 (about 2.1km across at this latitude), computed live from each neighborhood's coordinates, with its 14-digit quadkey generated the same way the notebook pads its own IDs (f"{int(x):014d}"). Travel speeds used to animate each trip (34 km/h car, 19 km/h transit) are illustrative round-trip-time placeholders, not measured Budapest traffic data.

Source: go-hary/Facebook-to-MATSim on GitHub · Elgohary et al., Journal of Urban Technology (2025), DOI 10.1080/10630732.2025.2546785
